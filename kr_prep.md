# Подготовка к контрольной работе №1

## 1. Когда я выберу rebase, а когда merge?

Rebase — когда история ещё «сырая» и её никто не смотрит: локальные feature-ветки перед открытием Pull Request, чтобы в main попал один чистый коммит и линейная читаемая история. Merge — когда работа уже опубликована (ветка запушена, коллеги работают с репозиторием) или когда важно сохранить факт параллельной разработки: merge не переписывает коммиты и ничего не теряет. Пример: свою ветку перед PR я пересаживаю на свежий main через rebase, а саму ветку в main вливаю через merge (или squash and merge).

## 2. Что произойдёт, если сделать rebase публичной ветки, с которой работают коллеги?

Rebase создаёт новые копии коммитов с новыми хешами, а старые «отцепляет». У коллег старая история осталась в их клонах, и при следующем pull Git увидит расхождение: локальные и удалённые коммиты станут «разными» версиями одних и тех же изменений. Начнутся ложные конфликты, придётся делать force-push (перезаписывая удалённую ветку), а у тех, кто уже успел сделать fetch, — принудительный rebase или merge с дублями коммитов в истории. Золотое правило: never rebase public branches.

## 3. Зачем нужен multi-remote и в каких реальных сценариях он применяется?

Multi-remote — это когда один локальный репозиторий пушится сразу в несколько удалённых. Реальные сценарии:
- бэкап/зеркало: основной репозиторий на GitHub для команды, автоматическое зеркало на GitLab или собственный сервер — если GitHub лежит или забанит аккаунт, код не теряется;
- миграция: команда переезжает с одной платформы на другую, какое-то время код живёт в двух местах синхронно;
- форки и open source: один код отправляют и в свой форк, и в оригинал.

Настройка: `git remote set-url --add --push origin <второй_url>` — и обычная команда `git push origin main` отправляет изменения в оба репозитория.
